# Disposable-run implementation in progress

This draft branch builds on recovery PR #37. It is synthetic-only and must not be used as a completed disposable application or merged as one yet.

The initial commit carries forward the standalone Calendarpit runner from `feat/calendarpit-run-lifecycle` (#18) and the Google-compatible client from `feat/calendarpit-provider-api` (#21), together with their existing unit and opt-in Docker integration tests. On the development host the tests verified synthetic OAuth, provider reads and ETag-protected writes, independent simulator instances and cleanup. They do not verify the application workflow.

The claim-bound provider adapter now verifies the exact synthetic approval and action immediately before provider writes; it reads every calendar page and uses an observed specific ETag for edits and removals. A fresh synthetic scenario can initialize from an already-seeded provider without an administrative reset. The actual planner and adapter have passed a synthetic OAuth test against an isolated Calendarpit container, including a separately approved near-term section. The companion and MCP entrypoints still use the earlier administrative adapter: this new path is not yet the application's normal route.

The runner publishes an unauthenticated administration endpoint on host loopback and its Docker network permits egress; it does not isolate or retire an agent, persist run identity, survive a hard kill cleanly or archive evidence. The provider client delegates approval to its caller and is not itself an authority. Before exposing a runnable environment, connect the application to the verified journal/provider path, restrict the agent network, verify its actual tool catalog in containers, implement retirement and archival, and package the trusted application and DSH in containers. Fail closed and report scope if these guarantees require the broader execution-worker architecture.

The study SDK profile disables native file, shell, plugin-management, scheduling, web and delegation tools and adds a deny-by-default tool-dispatch policy. A credential-free test booted the real DSH profile and inspected its registered global tool catalog: only the seven synthetic study MCP tools and native question tool were present, and the policy denied a native Bash call. This verifies that profile at startup, not host/container isolation or the permissions of arbitrary plugins, descendants or other DSH profiles. The restriction must also be verified in the eventual containerized run.

A Docker network probe on the development host started a separate agent-like Node container without a Docker socket. It could not reach the simulator's administration health endpoint through either the simulator's bridge address or the host gateway and loopback-published port. This is evidence for that host and test configuration, not proof of the actual DSH container's network or a production security boundary.

A standalone lifecycle registry now reserves a single run identity before resource creation and retains it across application-process restarts. Tests with a fake driver verify that archive failure, unverified cleanup and startup failure block replacement, and that discarding unsaved evidence requires an explicit choice after archive failure. A process killed during retirement leaves a visible, blocked `retiring` state. The registry is not connected to Docker or the companion yet; it does not determine whether an old lifecycle controller is still alive, and cannot yet resume that interrupted retirement safely. A real driver must establish resource ownership and verify termination before any release. No actual archive is produced by this registry alone.

The comparison groundwork also includes a persistent local budget ledger and a request-shaping policy for the exact authorized DeepSeek model and provider. Tests check sequential reservations, unknown-usage blocking and provider/model fallback rejection. They are not yet connected to the DSH model route or any HTTP gateway and do not enforce spending on their own. Local accounting is an approximate target, not an OpenRouter-enforced hard cap; other use of the same key and late or unknown billing remain outside its guarantees.
