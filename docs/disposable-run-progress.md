# Disposable-run implementation in progress

This draft branch builds on recovery PR #37. It is synthetic-only and must not be used as a completed disposable application or merged as one yet.

The initial commit carries forward the standalone Calendarpit runner from `feat/calendarpit-run-lifecycle` (#18) and the Google-compatible client from `feat/calendarpit-provider-api` (#21), together with their existing unit and opt-in Docker integration tests. On the development host the tests verified synthetic OAuth, provider reads and ETag-protected writes, independent simulator instances and cleanup. They do not verify the application workflow.

The claim-bound provider adapter now verifies the exact synthetic approval and action immediately before provider writes; it reads every calendar page and uses an observed specific ETag for edits and removals. A fresh synthetic scenario can initialize from an already-seeded provider without an administrative reset. A separate, student-bound Unix-socket broker exposes only seven synthetic agent operations; it has no approval, reset or provider-write operation, and the isolated MCP entry point does not fall back to the simulator if its broker is unavailable. Brokered file operations require the selected staged workspace, rather than falling back to shared fixtures. The actual planner and adapter have passed a synthetic OAuth test against an isolated Calendarpit container, including a separately approved near-term section. The running companion and legacy MCP entry point still use the earlier administrative adapter: this new path is not yet the application's normal route.

The runner publishes an unauthenticated administration endpoint on host loopback and its Docker network permits egress; it does not isolate or retire an agent, persist run identity, survive a hard kill cleanly or archive evidence. The provider client delegates approval to its caller and is not itself an authority. Before exposing a runnable environment, connect the application to the verified journal/provider path, restrict the agent network, verify its actual tool catalog in containers, implement retirement and archival, and package the trusted application and DSH in containers. Fail closed and report scope if these guarantees require the broader execution-worker architecture.

The study SDK profile disables native file, shell, plugin-management, scheduling, web and delegation tools and adds a deny-by-default tool-dispatch policy. A credential-free test booted the real DSH profile and inspected its registered global tool catalog: only the seven synthetic study MCP tools and native question tool were present, and the policy denied a native Bash call. This verifies that profile at startup, not host/container isolation or the permissions of arbitrary plugins, descendants or other DSH profiles. The restriction must also be verified in the eventual containerized run.

A Docker network probe on the development host started a separate agent-like Node container without a Docker socket. It could not reach the simulator's administration health endpoint through either the simulator's bridge address or the host gateway and loopback-published port. This is evidence for that host and test configuration, not proof of the actual DSH container's network or a production security boundary.

A standalone lifecycle registry now reserves a single run identity before resource creation and retains it across application-process restarts. Tests with a fake driver verify that archive failure, unverified cleanup and startup failure block replacement, and that discarding unsaved evidence requires an explicit choice after archive failure. A process killed during retirement leaves a visible, blocked `retiring` state. The registry is not connected to Docker or the companion yet; it does not determine whether an old lifecycle controller is still alive, and cannot yet resume that interrupted retirement safely. A real driver must establish resource ownership and verify termination before any release. No actual archive is produced by this registry alone.

Trusted code can now take a transactional snapshot of the synthetic state, unresolved claim and completed claim history, then write an atomic, private, hash-identified archive. Tests retain a sent-but-uncertain action even when the calendar observation is unavailable; a failed archive blocks replacement in the registry until retry or an explicit discard. The archive writer is currently exercised by a fake lifecycle driver and a separate Calendarpit integration test, not by the running application or a real retirement driver. Its [conservative projection](synthetic-archives.md) omits free text, notes, conversation and credential fields and stores hashes for event text and properties. As a result it cannot reconstruct descriptions or serve as the full replayable experiment bundle in the broader plan; retained identifiers and timestamps must still be synthetic. The caller must stop and verify writers before taking the snapshot, and the actual Docker lifecycle must enforce that requirement.

The comparison groundwork also includes a local budget ledger, a request-shaping policy and an experimental HTTP gateway for the exact authorized DeepSeek model and provider. Tests with a fake upstream check sequential reservations, usage accounting, unknown-usage blocking, streamed output and provider/model fallback rejection. A Docker test with a synthetic key verifies that its host environment file and a separate budget volume survive container recreation. The Compose gateway is intentionally disconnected from DSH, has an internal-only network and lacks verified pricing, so paid calls remain disabled. The account key is only mounted into this trusted service, not the simulator; see [the environment instructions](openrouter-environment.md). Local accounting is an approximate target, not an OpenRouter-enforced hard cap; other use of the same key and late or unknown billing remain outside its guarantees.

On 2026-11-11 a credential-free read of [OpenRouter's public endpoint metadata](https://openrouter.ai/api/v1/models/deepseek/deepseek-v4.1-flash-1017/endpoints) identified the `deepseek` provider tag and published time-dependent rate overrides. The pricing parser takes the highest reported input and output text rates across the base rate and every override, failing closed if the endpoint, tool parameters or rates are missing or ambiguous. This parser is tested against synthetic fixtures and was checked against the public metadata, but is not connected to the gateway or a trusted metadata-fetching lifecycle. It does not validate metadata provenance by itself or account for non-text pricing or external spending. Prices change; re-fetch and validate them before paid calls.

An explicit comparison profile now connects the application session wrapper and the real DSH SDK to the model gateway with an internal token and synthetic upstream. Tests show a complete synthetic response and a recorded synthetic charge; DSH automatic retries and the Luna compactor are disabled for this profile, and its child environment excludes ambient provider keys. Luna remains the default. A private control token can be generated and reused across gateway recreation without prompting the user. Brokered sessions probe readiness before starting and, while the tool-policy plugin is active, check the permitted tool catalog and broker at each model step. Tests cover a missing broker and a lost broker during a turn. DSH treats optional plugin activation failures as nonfatal, so actual production startup must independently verify that this guard and the expected tools are active; the tests do not make that a general DSH guarantee.

An opt-in Docker test ran a non-root DSH container in a separate internal network against a fake model gateway and a trusted local broker connected by synthetic OAuth to a disposable Calendarpit. It did not mount the provider file or Docker socket. The scripted model read and drafted, the test checked the calendar remained unchanged and existing commitments did not conflict, and a separate test-controlled approval applied only near-term blocks. DSH initially failed because its native loader copied a binary into the no-exec temporary filesystem; disabling that cache made it load from the read-only package instead. Twenty repetitions passed with host-mounted dependencies and another twenty passed using a locked, packaged DSH agent image, ten per persona in each batch; [the evidence and limits](evidence/broker-20.md) are recorded. The tests use a host-side test controller and do not establish a live-model result, complete isolation or an automatically archived/recoverable run. The running companion does not select or orchestrate this profile.

A separate constrained launcher now checks the preassigned run ID, labelled internal agent network, immutable image ID, private broker socket and gateway-control file before starting the packaged agent with restricted mounts and resource limits. A trusted-side stdio client exposes conversation operations but no calendar approval. Twenty additional scripted scenarios passed through this launcher and client. The launcher does not yet own the network, simulator, archive or restart lifecycle; a process exit is not treated as verified retirement. The test controller remains responsible for creating and removing the resources.
