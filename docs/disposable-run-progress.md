# Disposable-run implementation in progress

This draft branch builds on recovery PR #37. It is synthetic-only and must not be used as a completed disposable application or merged as one yet.

The initial commit carries forward the standalone Calendarpit runner from `feat/calendarpit-run-lifecycle` (#18) and the Google-compatible client from `feat/calendarpit-provider-api` (#21), together with their existing unit and opt-in Docker integration tests. On the development host the tests verified synthetic OAuth, provider reads and ETag-protected writes, independent simulator instances and cleanup. They do not verify the application workflow.

The claim-bound provider adapter now verifies the exact synthetic approval and action immediately before provider writes; it reads every calendar page and uses an observed specific ETag for edits and removals. A fresh synthetic scenario can initialize from an already-seeded provider without an administrative reset. A separate, student-bound Unix-socket broker exposes only seven synthetic agent operations; it has no approval, reset or provider-write operation, and the isolated MCP entry point does not fall back to the simulator if its broker is unavailable. Brokered file operations require the selected staged workspace, rather than falling back to shared fixtures. The actual planner and adapter have passed a synthetic OAuth test against an isolated Calendarpit container, including a separately approved near-term section. The running companion and legacy MCP entry point still use the earlier administrative adapter: this new path is not yet the application's normal route.

The simulator runner publishes an unauthenticated administration endpoint on host loopback and its Docker network permits egress. The trusted driver below adds per-run identity, isolated agent networking and verified retirement, but the running application does not use it yet. The provider client delegates approval to its caller and is not itself an authority. Before exposing this path to users, connect the application to the verified journal/provider path, verify the actual tool catalog and guard in the managed container, complete recovery and package the trusted application in Docker. Fail closed and report scope if these guarantees require the broader execution-worker architecture.

The study SDK profile disables native file, shell, plugin-management, scheduling, web and delegation tools and adds a deny-by-default tool-dispatch policy. A credential-free test booted the real DSH profile and inspected its registered global tool catalog: only the seven synthetic study MCP tools and native question tool were present, and the policy denied a native Bash call. This verifies that profile at startup, not host/container isolation or the permissions of arbitrary plugins, descendants or other DSH profiles. The restriction must also be verified in the eventual containerized run.

A Docker network probe on the development host started a separate agent-like Node container without a Docker socket. It could not reach the simulator's administration health endpoint through either the simulator's bridge address or the host gateway and loopback-published port. This is evidence for that host and test configuration, not proof of the actual DSH container's network or a production security boundary.

A lifecycle registry reserves a single run identity before resource creation and retains it across application-process restarts. An exclusive SQLite lease fences cooperating controllers. A trusted experimental driver creates and verifies the labelled Docker resources and archives state before replacement. Tests with a fake driver verify that archive failure and unverified cleanup block replacement, and that discarding unsaved evidence requires an explicit choice after archive failure. A process killed during startup or retirement leaves a visible, blocked state; safe resumption of those phases is not implemented. Failed startup is also blocked when its Docker outcome is unknown. The browser companion is not connected to this lifecycle.

Trusted code takes a transactional snapshot of the synthetic state, unresolved claim and completed claim history, then writes an atomic, private, hash-identified archive after draining the service and verifying the managed agent has stopped. A Docker crash drill retained an approved sent-but-unacknowledged action, observed the simulator without retrying the write, and verified retirement before a new run. That observation is a point-in-time snapshot, not proof of the final outcome of a delayed effect. An unavailable observation is recorded as such. The [conservative projection](synthetic-archives.md) omits free text, notes, conversation and credential fields and stores hashes for event text and properties. It cannot reconstruct descriptions or serve as the full replayable experiment bundle; retained identifiers and timestamps must still be synthetic.

The comparison groundwork also includes a local budget ledger, a request-shaping policy and an experimental HTTP gateway for the exact authorized DeepSeek model and provider. Tests with a fake upstream check sequential reservations, usage accounting, unknown-usage blocking, streamed output and provider/model fallback rejection. A Docker test with a synthetic key verifies that its host environment file and a separate budget volume survive container recreation. The Compose gateway has an internal-only network and lacks verified pricing, so paid calls remain disabled. The experimental lifecycle can attach a labelled gateway to a run's private agent network; tests use a fake gateway. The account key is only mounted into the trusted real gateway, not the simulator or agent; see [the environment instructions](openrouter-environment.md). Local accounting is an approximate target, not an OpenRouter-enforced hard cap; other use of the same key and late or unknown billing remain outside its guarantees.

On 2026-11-11 a credential-free read of [OpenRouter's public endpoint metadata](https://openrouter.ai/api/v1/models/deepseek/deepseek-v4.1-flash-1017/endpoints) identified the `deepseek` provider tag and published time-dependent rate overrides. The pricing parser takes the highest reported input and output text rates across the base rate and every override, failing closed if the endpoint, tool parameters or rates are missing or ambiguous. This parser is tested against synthetic fixtures and was checked against the public metadata, but is not connected to the gateway or a trusted metadata-fetching lifecycle. It does not validate metadata provenance by itself or account for non-text pricing or external spending. Prices change; re-fetch and validate them before paid calls.

An explicit comparison profile now connects the application session wrapper and the real DSH SDK to the model gateway with an internal token and synthetic upstream. Tests show a complete synthetic response and a recorded synthetic charge; DSH automatic retries and the Luna compactor are disabled for this profile, and its child environment excludes ambient provider keys. Luna remains the default. A private control token can be generated and reused across gateway recreation without prompting the user. Brokered sessions probe readiness before starting; the policy checks the permitted tool catalog and broker at each model step. Since DSH treats optional plugin activation failures as nonfatal, the session now requires a private startup marker written after the policy registers its guard and hook, and fails closed when it is missing. A rebuilt container passed both persona scenarios; a synthetic gateway also checked the actual model-facing tools and pinned provider fields. A separate Docker test deliberately broke policy activation and confirmed the turn was rejected before a proposal or calendar change. The marker detects a wiring failure, not a compromised process running under the same user, and these checks are not a general DSH security guarantee.

An opt-in Docker test ran a non-root DSH container in a separate internal network against a fake model gateway and a trusted local broker connected by synthetic OAuth to a disposable Calendarpit. It did not mount the provider file or Docker socket. The scripted model read and drafted, the test checked the calendar remained unchanged and existing commitments did not conflict, and a separate test-controlled approval applied only near-term blocks. DSH initially failed because its native loader copied a binary into the no-exec temporary filesystem; disabling that cache made it load from the read-only package instead. Twenty repetitions passed with host-mounted dependencies and another twenty passed using a locked, packaged DSH agent image, ten per persona in each batch; [the evidence and limits](evidence/broker-20.md) are recorded. The tests use a host-side test controller and do not establish a live-model result, complete isolation or an automatically archived/recoverable run. The running companion does not select or orchestrate this profile.

A constrained launcher checks the preassigned run ID, labelled internal agent network, immutable image ID, private broker socket and gateway-control file before starting the packaged agent with restricted mounts and resource limits. A trusted-side stdio client exposes conversation operations but no calendar approval. Twenty additional scripted scenarios passed through this launcher and client under a test controller. The experimental lifecycle driver now owns creation and verified retirement of these resources, but is not connected to the companion.

The trusted study service stops accepting new broker operations, waits for its own active calendar write and agent operations, and only then takes a transactional archive snapshot. A forced drain fails closed while an in-process writer is active. The controller crash drill killed the trusted process during an uncertain write, then a new lease holder verified the agent was stopped, preserved the pending claim and retired the simulator before replacement. The lease alone does not stop containers or delayed provider effects. Resumption of an existing interactive session, startup/retirement interruption handling, the bilingual recovery interface, live model runs and application integration remain unfinished.

On 2026-11-11 the real experimental lifecycle driver completed [20 independent scripted runs](evidence/managed-lifecycle-20.md), ten for each persona, with archive-before-retirement checks. This is deterministic infrastructure evidence, not a model-quality comparison. The managed launcher currently supports the DeepSeek gateway profile only; the existing Luna subscription path has not been integrated into this isolated lifecycle.

An experimental private JSONL trace now records run configuration, synthetic tool requests/results, observed conversation snapshots and trusted approval decisions/results for managed runs. A failure to record an approval decision blocks its write; an evidence failure after an attempted operation reports that state may have changed. The trace is not yet connected to the browser, does not capture all write acknowledgments or usage, and is not the agreed experiment bundle. It removes common credential fields and bearer/API-key patterns, but pattern redaction cannot recognize arbitrary secrets: callers must never supply real credentials, raw headers, environment or real personal data. Do not start a recorded live run on the strength of this trace alone.

A synthetic conversation wrapper captures observed prompts, answers and bounded SDK snapshots without repeating messages in the managed run driver. Snapshots can lose messages between polls and are not full SDK events. Evidence-failure retirement, durable conversation capture and a richer bundle still require integration and tests.

The live controller now blocks archival if its in-memory trace has experienced a persistence failure. This check alone does not prove that a new controller can detect an earlier trace failure after a crash; persistent evidence health and safe recovery still need implementation before the bundle can be relied upon.
