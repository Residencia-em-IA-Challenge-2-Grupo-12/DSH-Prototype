# Sandbox and workspace options: research notes

**Reviewed:** 2026-11-11. Scope: candidates for a synthetic evaluation environment and a possible later desktop product. These are documented capabilities, not verification that they integrate with our pinned DSH version, login plugin, target hosts, or calendar workflows. A sandbox limits access to what is exposed; it cannot undo an authorized calendar API operation or prevent all bad decisions.

## Workspace copies and proposed changes

For a synthetic run, use immutable versioned fixtures as the starting point; make a private per-run working copy and fresh calendar state; archive approved decisions and relevant observations before retirement. Production need not reset the user's real workspace. If future tasks edit user files, a trusted host service can copy selected material into a private workspace, let the agent produce changes, show a diff or preview, check whether originals changed since the snapshot, then apply selected changes after approval. This requires explicit handling for moves, deletions, binary files, links, permissions, conflicts and files changing during a scan; a normal text diff is insufficient. Copies and snapshots can contain sensitive information and need retention and deletion policies. For a cloud drive, its API and server-side versions/permissions govern access; copying files locally does not roll back provider-side edits.

Docker containers use a writable container layer over image layers; common OverlayFS backends use copy-on-write. Persistent volumes and bind mounts are separate from the container layer: a bind mount is writable by default and can change the real host directory. A read-only mount prevents direct writes through that mount but is not a snapshot of changes made on the host. Recursive read-only handling of nested mounts depends on kernel support. See [Docker bind mounts](https://docs.docker.com/engine/storage/bind-mounts/) and [Docker storage drivers](https://docs.docker.com/engine/storage/drivers/). Do not confuse deleting a container with undoing a write to a bind mount, named volume, network service, or calendar.

## Candidate execution boundaries

| Candidate | What the official material establishes | Fit and questions |
| --- | --- | --- |
| Hardened Docker container | Containers can use reduced Linux capabilities and restrict mounts/network; rootless mode runs the daemon and containers in a user namespace. [Docker security](https://docs.docker.com/engine/security/), [rootless](https://docs.docker.com/engine/security/rootless/). | Already used by the experimental synthetic agent. Check actual process identity, Docker daemon privileges, mount permissions, resource limits, network and socket reachability on each host; no host Docker socket in the agent. Rootless daemon is distinct from merely running a container process as a non-root user. Ordinary containers share the host kernel and are not equivalent to microVMs. |
| Bubblewrap | Builds a Linux sandbox by composing namespaces and mounts; an optional network namespace can have only loopback. Its maintainers stress that its command-line policy determines the protection and that shared sockets can provide host capabilities. [Bubblewrap README](https://github.com/containers/bubblewrap/blob/main/README.md). | A plausible local Linux execution-worker primitive with lower infrastructure overhead. Must supply and test a correct policy, handle disabled unprivileged user namespaces and policy bypass via other tools; it is not a ready-made cross-platform product. |
| gVisor | `runsc` provides a per-sandbox application kernel layer for containers; gVisor still relies on host controls for resource exhaustion and says a network-accessible host service or exposed API remains an attack path. [Security model](https://gvisor.dev/docs/architecture_guide/security/). Some Linux features are unsupported, so compatibility must be tested. [Application compatibility](https://gvisor.dev/docs/user_guide/compatibility/). | Candidate stronger container boundary for later adversarial workloads; test DSH native addon, IPC, runtime limits and performance with pinned images. It does not prevent writes to files or APIs intentionally exposed to a process. |
| Firecracker | Uses Linux KVM-based microVMs; its design describes layers of isolation and calls for the `jailer` in production. [Firecracker design](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md). | Candidate for higher-isolation server or Linux-host use when its operations and image management are justified. KVM availability and VM lifecycle are prerequisites; it is not automatically a native desktop solution on every OS. |
| Docker Sandboxes (`sbx`) | Docker describes local microVM sandboxes with mountless/private-clone/direct-workspace modes, a network proxy with credential injection, persistent sandbox state until removal and a host-side MCP gateway. [Architecture](https://docs.docker.com/ai/sandboxes/architecture/), [security model](https://docs.docker.com/ai/sandboxes/security/). | An established packaged candidate worth a bounded probe, distinct from our current ordinary Docker containers. Direct workspace mode is live read-write; clone mode is for Git repositories; local stdio MCP servers run on the host. Check current supported platforms, installation/licensing, non-Git student documents, external network policy, explicit cleanup, DSH custom template support and subscription refresh before adoption. Do not assume the model key injection also handles the third-party Codex OAuth flow. |

For direct desktop installation, platform mechanisms differ. Apple's [App Sandbox](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox) supports scoped access to user-selected files and persistent security-scoped bookmarks. Windows [AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation) can restrict resources, but [MSIX full-trust packaging](https://learn.microsoft.com/en-us/windows/msix/msix-containerization-overview) alone still gives a desktop app ordinary user permissions. Availability, usability, integration with browser automation and privileges for each target OS require practical tests; these mechanisms do not automatically sandbox arbitrary descendants or grant access to other applications.

## Recommended bounded next checks

1. Keep the current synthetic runs and API/mock-first tests; verify the failure boundaries and workflow without waiting for an ultimate desktop sandbox choice.
2. For DSH's built-in sandbox, test the **pinned installed version**, whether all execution and file tools are covered, availability on target hosts, fail-closed behavior, what network and child processes can access, and compatibility with our plugin/tools. Do not equate a Bash-only guard or a prompt instruction with confinement of all tools.
3. Probe one container-based option and one native Linux option against the same disposable fixture: attempted access outside the selected workspace, credentials, Docker socket, host processes and network; creation and review of staged artifacts; interruption and cleanup. Include explicit negative controls so a test fails when the boundary is deliberately disabled. Repeat for each OS eventually supported.
4. If evaluating Docker Sandboxes, separately check its agent template integration, credential handling, calendar MCP policy and writable mounts. Exposed API/MCP or GUI permissions may still affect real user resources regardless of the VM boundary.

**No security product has been selected or validated here.** Actual acceptance requires verifying the configured boundary and host environment, not just the selected product's marketing or default configuration.
