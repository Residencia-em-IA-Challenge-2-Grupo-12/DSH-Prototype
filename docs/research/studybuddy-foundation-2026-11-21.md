## First comparison

Use StudyBuddy's existing pipeline as **A** after adding the smallest calendar contract. Use the single-agent DSH configuration as **B**. This is the paired replay in [DSH #47](https://github.com/Residencia-em-IA-Challenge-2-Grupo-12/DSH-Prototype/issues/47).

1. **Start with one fictional Bruno case.** Give both adapters the same frozen document bytes and source IDs, simulated clock and time zone, calendar fixture, starting request, prepared clarification answer, Monday correction and operator approval for the coming week only. Create independent simulator instances from the same fixture. Preserve unavailable facts as unknown.
2. **Keep the shared contract at the runner boundary.** Version the input manifest and the ordered outputs for question, answer, cited facts, immutable proposal, validation, approval decision and observed calendar result. Include run ID, proposal revision, section, intended actions, acknowledged actions, observed event IDs and truthful partial or unknown state. Keep agent trace, runtime and model identity, duration and available usage as evidence. Each repo owns its internal structures. StudyBuddy can retain `DiretivaMaestro`, `PropostaGrade` and `ProvedorAgenda`, while DSH retains its own planner, tools and controller. Join by stable source reference, date/time and event identity within a run. Provider-generated IDs may differ between runs.
3. **Pass a scripted contract test before model testing.** Verify the cited deadline, a real answer and revision handoff, schedule feasibility, preservation of existing events, no write before approval, and only near-term changes afterward. Inject a stale proposal, duplicate approval and uncertain write. Independent observation must agree with the ledger. A duplicate request can return the prior receipt or a documented safe rejection. Either outcome must avoid a second write.
4. **Report which comparison was possible.** The inspected StudyBuddy API uses local Ollama with a different evidence and model setup from the DSH Luna run. If a shared authorized route and comparable fixture access are available, record them. If the configurations differ, report A/B as a whole-system comparison and name the differences. Fresh live A/B is still unverified. Keep DSH's existing authorization limits and treat unavailable usage as unknown.

## Runtime delegation after paired replay

**C** runs the DSH baseline with an optional worker operation. Compare B/C with the same lead model, inputs, available sources, primary tools and total execution budget. Keep B as the negative control for whether an extra worker is needed. [DSH #48](https://github.com/Residencia-em-IA-Challenge-2-Grupo-12/DSH-Prototype/issues/48)

- Give the lead a restricted operation accepting one purpose, a short question and approved source IDs. Start with evidence cross-checking and schedule critique. Let the lead choose zero, one or two read-only workers with depth one. Close the worker's route, context, files and visible tools under a trusted policy. Workers return structured claims with source IDs, uncertainty and disagreements. They do not speak to the user, create proposals, approve or write.
- Enforce a shared limit on total calls and active time, explicit deadlines and cancellation outside the prompts. Meter tokens where exposed. Give worker processes only selected read-only artifacts and a scoped tool/model channel. Keep approval, the provider writer, unrelated workspaces, agent-controlled shell/network access and credentials outside that boundary. Verify the visible catalog and what a child process can actually access before using model outputs.
- Use a small Monday reschedule where delegation is unnecessary and a case with conflicting syllabus and LMS dates where independent inspection might help. Drill worker timeout, disagreement, unnecessary delegation and attempted out-of-scope access. Show when the lead continues alone, asks the user or reports unresolved evidence. Assess source correctness and adequacy of the explanation alongside extra calls, latency and usable output. Charge worker execution against the same run budget.

## Repository decision

| Option | What it buys | Cost and best use |
|---|---|---|
| Separate repos, pinned DSH process adapter | Independently evolvable product and experiment code. Exercises real DSH, including its tool and model behavior. | Implement the small versioned adapter and fixture runner. **Recommended first.** Put runner/scenario ownership with StudyBuddy if its team adopts the shared contract. Keep DSH's adapter and policy verification in DSH. |
| DSH source as a Git submodule | Atomic reference to DSH source in a StudyBuddy checkout. | Git pins source only. A process adapter, dependency/runtime pins, fixture isolation and policy tests still apply. Adopt if repeated coordinated source changes make a single checkout worth maintaining. |
| Build an orchestration comparator in StudyBuddy's Python stack | Easier same-runtime experiments with roles, prompts and budgets. Can reuse the existing Python triage and planning code and provide an additional control. | Duplicates durable calendar/approval/evidence behavior if it grows to replace DSH. It can test orchestration choices, while DSH's capabilities are measured by the pinned adapter. |

**Proceed now with #47's shared contract, fixture and scripted smoke tests.** StudyBuddy's current code and CI make that a credible bounded integration task. Start scoring live A/B when both adapters complete the stateful scenario against the contract. Start B/C after worker isolation and cancellation pass negative tests. Keep StudyBuddy's product and existing DSH demo moving independently through those gates.
