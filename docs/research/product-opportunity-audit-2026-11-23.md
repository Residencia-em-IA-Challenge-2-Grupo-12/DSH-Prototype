## Product scope correction

The materials-generation and SQL export suggestions below are part of the original audit record. The agreed student workflow is planning, tracking and adapting study. Course materials can inform that work. Generating or editing course content belongs to a separate product decision. Technical staging or export probes belong outside normal student navigation. The runnable interface comparison removed the SQL example after this clarification.

## Proposed experiments

| Order | Question and options | Smallest useful test |
| --- | --- | --- |
| 1. First request | Compare the blank composer, one primary editable suggestion, and three editable task starters. Examples are “Plan a study week around my commitments,” “Find two one-hour study windows before my next deadline,” and “Help me move a study block.” A starter fills the composer. The user controls send and can still write freely. Use the primary action for starting the scenario or continuing the pending task. Put language where people can find it and facilitator actions in a labeled session menu after setup. | Give a few first-time operators two matched synthetic tasks, in counterbalanced order where possible. Observe time to a usable first request, needless prompting, initial scope surprises, and whether they can say what requires approval. Treat 30 seconds as a trial target and a small sample as qualitative evidence. |
| 2. Navigation and priority | Compare the current anchored page with a persistent next-action strip and a dedicated review drawer or tab. The strip leaves surrounding calendar context visible. The drawer gives complex comparisons space and requires focus return and a visible way back. Keep text labels for processing, waiting, stale, and applied. Reserve accent colors for decisions and state, with a cue that still works in monochrome. | Reuse the same calendar, model outputs and proposal. Ask the operator to locate the open question, catch the Monday mismatch, identify the exact affected dates, and choose only the near-term action. Measure wrong-scope choices and whether the person can tell when changes touch the calendar. Try desktop and a narrow view in both languages. |
| 3. Visual direction and density | Compare **quiet editorial** with stronger typography, a warmer background and visible next action, **calendar workbench** with tighter alignment, muted commitments and strong time/diff emphasis, and a **compact agenda** on small screens. Keep calendar and chat structure constant for the first visual comparison. Test layout separately. Use short transition or focus cues only when they convey a change, with reduced-motion behavior. | Use static screens for comprehension first, then one interactive flow if worthwhile. Ask which option is active, what blocks conflict, and where to check evidence. Record legibility and preference separately. Compare compact labels, more readable defaults, target sizes and visible text cues with the same contents. |
| 4. Connect calendar and chat | Add a visible “Ask about this” action on an event or day and an editable date/time chip in the composer. In reverse, use a question option or proposal row to jump to the exact time. Explore a Day/Week/Agenda toggle and “Return to planning week.” Distinguish free, busy and tentative events with text, since the planner treats transparency differently from a commitment. | Use Ana's weekday conflict and Bruno's exact Monday correction. Check context survives navigation, the selected time is inspectable before sending and a late conflict explains why selection is unavailable. Include a keyboard pass that preserves the selected radio while tabbing to the next control. |
| 5. Materials and artifacts | Compare citations alone with a small “Materials in this session” tray. Show included files, a source revision, and a single draft artifact tied to one selected study block, with a reviewable save/discard boundary. This can make the assistant useful during study as well as while scheduling it. | One fictional database exercise. Ask the operator to predict what materials the agent can see, exclude an unnecessary file, inspect a generated worksheet or SQL diff and decide what to export. A scripted artifact is enough to evaluate the interaction. Evaluate execution only if the task needs feedback a static artifact cannot give. |

Two additional checks fit this work. First, show a dated, one-line **“what changed and why”** for each revision and let the user open the supporting input. The prototype already has diffs and source passages, but the operator currently assembles the story across separate panels. Second, show a useful first-run explanation of the current **capabilities and data scope** close to the composer, with runtime and trace details in a disclosure. That addresses uncertainty about blocked actions and about data sent to a model without turning the first screen into an operator console.

## Sandbox and selected workspace

The host Luna run uses a restricted tool catalog and a broker over the synthetic workspace. The subscription plugin still runs as a host process. The check-in prompt requests structured output without tools, while the host session still has its authorized study catalog. Prior live trials checked observed actions after the call. A separate interpretation-only route could enforce an empty catalog if that purpose becomes a requirement. [SDK session](../../src/sdk-session.mjs#L26-L46) · [Tool policy](../../src/dsh-tool-policy.mjs#L5-L45) · [Check-in runner](../../experiments/checkin-preference/walkthrough.mjs#L46-L80).

The managed Docker comparison worker is non-root, with a read-only root filesystem, a limited process environment and an internal bridge. The study broker remains a capability that can write run-local drafts. A plain internal bridge can still make some host services reachable depending on binding and gateway configuration. The existing #28 worker is a separate synthetic spike with bounded execution and artifacts. That creates an option for optional coding, subject to product-level import, export and ownership decisions. [Docker launcher](../../src/foundation/docker-agent.mjs#L36-L51) · [Study boundary](../../src/foundation/study-boundary.mjs) · [Docker internal network semantics](https://docs.docker.com/reference/cli/docker/network/create/#network-internal-mode---internal) · [Worker prototype #28](https://github.com/Residencia-em-IA-Challenge-2-Grupo-12/DSH-Prototype/pull/28).

The simplest direction is a **selected snapshot**. The user picks files or a folder, previews the resolved file list and exclusions, and confirms the exact snapshot. Keep a manifest with relative paths, source revision where available, size and hashes. Limit file count and bytes, use ordinary files, and exclude links, credentials, repository metadata and caches by default. Use a private copy for editing, a separate choice for any content that can be sent to a model, and a reviewed export for changes. A directory choice should expand into the visible list. The host checkout stays outside the worker. A trusted controller owns snapshot and export and checks whether the source changed before an accepted patch can apply. Existing paired replay already verifies declared files and digests for controlled fixtures. [Verified file set](../../src/paired-replay/bundle.mjs#L20-L39) · [Git path-limited archives](https://git-scm.com/docs/git-archive) · [Linux path resolution controls](https://man7.org/linux/man-pages/man2/openat2.2.html).

| Option | Tradeoff |
| --- | --- |
| Selected snapshot and brokered reads/patches | Smallest proof of what the assistant can see and what the user can export. A user can review proposed edits and obtain a patch before executing anything. |
| Separate offline Docker worker | Adds bounded execution in a pinned image using an isolated scratch copy. Give the worker no network, calendar, model gateway, provider credentials, host checkout or Docker socket. A trusted controller mediates bounded results and export. Rootless mode reduces daemon authority when the host setup and limits are verified. Containers share the host kernel. [Docker none driver](https://docs.docker.com/engine/network/drivers/none/) · [Docker rootless mode](https://docs.docker.com/engine/security/rootless/). |
| gVisor or a local microVM | Useful to compare if arbitrary code or shared hosting becomes a real requirement. These increase the separation available to the worker and add compatibility, setup and lifecycle cost. First establish the need with a real workflow. [gVisor security model](https://gvisor.dev/docs/architecture_guide/security/) · [Firecracker design](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md). |

A later sandbox acceptance exercise can show that the imported set matches the manifest, unselected mock files and services are unavailable, a fixed test command can finish or be cancelled, the proposed patch is bounded and a changed source is detected before export. Verify worker retirement and make the effective capabilities visible to the operator. Keep this independent of any early model availability or live calendar decision.
