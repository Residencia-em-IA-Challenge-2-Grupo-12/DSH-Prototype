# Synthetic calendar/domain integration spike

The temporary implementation connects the provider-style Calendarpit client to the loopback domain service. The observer records paginated events with IDs/ETags and free/busy, hashes the complete observation, checks that event pages remain unchanged across the free/busy read, and writes a versioned calendar revision. Incomplete or stale observations fail closed.

The single-event **create-only** bridge binds an exact action to an immutable approved proposal. A SQLite transaction verifies the proposal, all referenced revisions and decision, and records a unique durable application claim. Pending, unknown and review claims block further local revisions, proposals, decisions and competing claims for that student. Before creating, the bridge compares fresh event/ETag and free/busy observations to the approved revision, checks availability and rechecks the exact claim in the provider callback. It preserves approved event content, reads resulting state, and compares all other events with the approved snapshot. Conflicts, unresolved intervals or unrelated event changes enter durable `review` and block further operations.

All-day intervals are checked using their exclusive end date and the validated explicit calendar timezone in the observation. An all-day event remains unresolved when its dates or timezone are missing or ambiguous. Timed events are compared as instants. Unrelated changed events also require review, including events that do not overlap the new event.

Claims are enumerable by `GET /v1/students/{student}/applications` so a caller can discover a commit whose response was lost. After a claim failure, the bridge releases its instance lock only when the trusted service explicitly confirms that this request was rolled back; it retains the lock for timeouts, transport failures, malformed responses and unclassified errors. An empty claim listing immediately after a timeout does not rule out a later commit. An observed result that cannot be persisted under the HTTP 64 KiB body limit is never silently truncated into a success: the bridge uses a conservative preflight and, if a result still cannot be saved after a provider attempt, tries to persist an explicit `unknown` with no claimed observation. It also returns the unpersisted observation to the caller when available. A crash leaves a durable `pending` claim. Pending, review and unknown states block retry and local revisions. **A reconciliation UI/API is not implemented**: no automatic recovery is available. Do not delete locks or alter claims without a future reviewed reconciliation procedure.

An additional atomic lock is keyed by the canonical `127.0.0.1` simulator origin in `/tmp/study-calendar-bridge-locks-v1`. It serializes bridge calls to the same simulator across separate local domain databases. Locks persist on crash, lost response, review or unknown state. This coordination only works when every bridge uses the **same host temporary filesystem**. Containers with separate `/tmp` mounts, bypassing the bridge, different network namespaces, or other provider actors are outside that lock. A deployment needs a shared transactional lock and an isolated trusted provider gateway before agent access.

The domain service has **no authentication**. Any local process can invoke its internal claim/finish endpoints, so do not expose it to workers, a network or real data. The experiment deliberately remains unintegrated with the application. The simulator create endpoint has no atomic calendar-wide free/busy precondition: another actor may add a conflict between checking and writing. The post-write review catches only changes visible in the final observation; later changes or changes that revert between reads can be missed. This is not a production concurrency or security guarantee. Patch/delete, recurring-event semantics, multi-action partial writes, real-provider behavior and production migrations are outside scope. Schema version 3 contains an experimental migration from version 2; Node's SQLite API remains experimental.

Validation: 18 deterministic approved-create tests cover exact action binding, blocked review state, a delayed claim commit after transport timeout, cross-store coordination, schema migration, same-day and distant all-day events, edits after the precheck, persistence limits, error-after-write and unreadable resulting state. Two observer tests cover pagination, ETags, error handling and concurrent revisions; a request-handler test verifies that only definitive claim rollbacks carry the rejection marker. The live integration test passed against the locally cached Calendarpit Docker image before this latest claim-response change; rerun it for the updated version. These are synthetic tests and do not establish production-provider guarantees. No real accounts or user data are involved.
