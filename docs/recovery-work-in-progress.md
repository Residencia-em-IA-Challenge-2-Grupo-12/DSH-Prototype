# Baseline recovery work in progress

**Do not merge this intermediate branch as a completed recovery fix.** It is a synthetic-only development slice for issue #36, based on PR #8. It blocks several conflicting application operations after an ambiguous write, but cannot yet resolve such a claim or reliably explain it in the interface.

The first slices add a local SQLite state store and transactional checkpoint, feedback, proposal draft, annotation draft, narrative, annotation-approval and study-plan approval updates. Legacy per-student synthetic JSON is imported on first read and left unchanged as a backup. Cross-process checkpoint/feedback, concurrent drafting and approval regressions and the legacy-import check pass. Failed study-plan and annotation applications preserve the last trusted snapshot and separately record any subsequent observation; the tested edit between batch actions is protected. The synthetic Calendarpit study-plan and annotation integration checks pass on an isolated instance. New claims also guard reset and survive a tested process interruption, but the additional boundaries below remain.

Node's built-in SQLite interface is experimental. The database requires a local filesystem with working SQLite locking; this initial slice is not a cross-container deployment or authentication boundary. Continue to use fictional data only.

The state store now acquires a simulator-wide persistent claim for baseline plan approvals, annotation patches and fixture reset. Plan and annotation claims validate the saved proposal in the same SQLite transaction; each provider action records its intent before the call, then acknowledged and observed outcomes. Successful claims archive the record and commit state in the same transaction. Conflicting drafts, checkpoints, decisions and resets are blocked; feedback is allowed during an approval but blocked during reset. A killed synthetic writer leaves a claim after restart, and a competing process cannot reset through this module. A database lock that prevents claiming also prevents a provider write. Tests use isolated synthetic runtime directories.

**Unresolved boundaries:**

- Claims are deliberately not cleared automatically after an uncertain attempt. There is no human-reviewed reconciliation or safe destructive reset path yet, so the application can remain blocked indefinitely. A missing or delayed provider response cannot be treated as proof that a later write is impossible.
- The companion UI does not yet expose claim evidence or reliably render all new states: an `applying` section may be labeled as applied, and the status endpoint fails entirely when the calendar is unavailable. Do not use this branch as a demonstration until those paths are fixed.
- The claim coordinates only processes using the same local SQLite directory and this module. Direct Calendarpit administration, an agent with host access, separate database volumes, and other provider clients can bypass it. It is not authentication, sandboxing, or an atomic provider precondition; check/write races remain.
- Legacy synthetic records with a previously partial operation may not have a claim. Migration and review of those records are not yet complete. Reset still performs external and filesystem steps that cannot be made atomic by SQLite; a failed reset leaves the claim blocked.
- The crash test kills an application process at a controlled fake-provider call; it does not prove real-provider late-delivery semantics. Tests against the pinned simulator cover normal success, not every interruption. Node's SQLite interface is experimental.
